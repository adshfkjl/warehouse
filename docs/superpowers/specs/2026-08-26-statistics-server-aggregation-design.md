# 统计服务端聚合设计

## 目标

将 SQL Server 统计源中可由数据库完成的事实聚合下推到 SQL，降低大数据量统计周期的网络传输和应用进程内存占用，同时保持现有统计契约、仓库范围、终态任务口径、幂等和失败处理行为不变。

## 范围

本设计只涉及 `SqlServerStatisticsSource` 的查询和聚合方式，以及对应的自动化测试和操作文档。统计 API、SQL 投影实体、周期 Worker、PLC 协议、库存业务规则和点位读模型不改变。

必须下推到 SQL 的事实聚合：

- 库存余额的数量、重量和是否存在事实判断；
- 库位容量总和与占用数量总和；
- 周期内入库、出库、移库数量和事实是否存在；
- 周期内任务的必要字段筛选。

任务仓库归属仍需要读取 `DispatchContextJson`，因为现有 SQL Server 版本和数据模型没有可依赖的 JSON 结构化列。任务上下文解析、非法值处理、跨仓库排除和终态去重继续由应用层统一完成。

## 方案

`BuildAsync` 保留一个可取消的 `DbContext` 生命周期，但不再把所有事实行加载为集合：

1. 先以库位层级子查询限定目标仓库的库位集合，不在应用层构建 `locationIds` 集合。
2. 使用 SQL 投影计算库存总量、重量和事实存在性；空事实集返回 `null`，不得伪造 KPI。
3. 使用 SQL `GroupBy`/`Sum` 计算入库、出库和移库数量；移库按源库位或目标库位纳入仓库范围。
4. 使用 SQL 投影计算库位容量与占用数量总和，零容量返回 0。
5. 任务查询只取周期内任务的 ID、状态、更新时间和调度上下文；任务数量受周期和仓库候选库位过滤，随后由现有解析器完成最终归属判断。
6. 继续调用现有 `StatisticsAggregation.Build` 统一合并 KPI、任务状态和异常计数，避免产生第二套统计口径。

如果某个 EF 查询无法被 SQL Server 翻译，必须显式拆为可验证的 SQL 查询或小范围任务解析查询，不能通过无界 `ToListAsync` 回退到全量事实加载。

## 一致性与错误处理

- 所有查询使用 `AsNoTracking` 和调用方取消令牌。
- 同一 `BuildAsync` 使用同一个数据库快照边界；不要求跨多个查询持有长事务。
- 查询失败、取消或数据库不可用时向上抛出，Worker 保留最近成功批次，不落成功的空批次。
- 统计结果必须与当前内存聚合在相同事实集上完全一致，尤其是 Move 的源/目标范围、终态任务成功率和未知仓库排除。

## 验收

- 单元测试覆盖空事实、零容量、Move 源/目标范围和终态任务口径。
- SQL 集成测试使用 Docker SQL Server 验证聚合结果与现有统计契约一致。
- 大数据量夹具验证统计查询不加载全部库存余额或流水实体；允许读取任务上下文，但必须受周期和范围过滤。
- `dotnet restore`、`dotnet build`、全量测试、EF 迁移、健康检查和 `scripts/verify.ps1` 全部通过。
- `warehouse/` 旧系统目录保持无差异。

## 非目标

- 不引入存储过程、物化视图或新的统计事实表。
- 不改变 API 字段、统计口径、数据库业务真相或 PLC/设备边界。
- 不连接生产数据库或真实 PLC。
